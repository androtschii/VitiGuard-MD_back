# Принятые решения

## uv вместо Poetry/Pipenv (pr-001)

Один бинарный файл без зависимостей, пакеты ставятся в разы быстрее, нужную версию Python uv при необходимости скачивает сам. Версии зависимостей фиксируются в `uv.lock`, проект описан стандартным `pyproject.toml` (PEP 621), поэтому его по-прежнему можно установить через pip или Poetry 2.

## Python 3.12 (pr-001)

Для 3.12 есть готовые сборки всех библиотек, которые понадобятся дальше: PyTorch, ONNX Runtime, Rasterio.

## Окончания строк LF (pr-001)

Разработка идёт на Windows, а запускаться код будет в Linux-контейнерах и CI. `.gitattributes` хранит все текстовые файлы с LF: скрипты с CRLF ломаются в Docker.

## Настройки передаются в фабрику приложения (pr-001)

`create_app(settings)` сохраняет настройки в `app.state`, эндпоинты получают их через зависимость `SettingsDep`. Тесты создают приложение со своими настройками — без глобального кэша и без чтения локального `.env`.

## Ruff, Black и mypy (pr-002)

Ruff — линтер, он же сортирует импорты (вместо flake8 и isort); Black — форматирование; mypy — в режиме `strict` с плагином pydantic. Длину строк (88 символов) контролирует Black, поэтому правило E501 в Ruff отключено. Правила RUF001–RUF003 тоже отключены: они принимают русскую «с» в предлогах за латинскую `c` и срабатывают почти на каждом комментарии.

## Docker Compose (pr-003)

- База — образ `postgis/postgis:18-3.6` (PostgreSQL 18 + PostGIS 3.6). Расширение включается миграцией в pr-006, но в образе оно нужно сразу. Том смонтирован в `/var/lib/postgresql`: с 18-й версии образ хранит данные в подкаталоге по номеру версии, и старая точка монтирования `/var/lib/postgresql/data` не подходит.
- Redis 8 — брокер для Celery (pr-015) и кэш.
- Образ API: зависимости ставятся из `uv.lock` (`--locked`) отдельным слоем, так что при правке кода пересобирается только слой с кодом. Процесс работает от непривилегированного пользователя. Многоэтапная сборка — в pr-098.
- API запускается только после того, как прошли healthcheck базы и Redis.
- Пароли по умолчанию годятся только для локальной разработки и переопределяются в `.env`.

## CI на GitHub Actions (pr-004)

Запускается при push в `main` и на каждый PR. Три параллельные задачи: линтеры и mypy; тесты с отчётом о покрытии; сборка образа и запуск всего стека через Docker Compose с запросом к API. Покрытие ниже 85 % (порог из стратегии тестирования) роняет сборку. Запуски для устаревших коммитов той же ветки отменяются, токен workflow имеет права только на чтение.

У контейнера API появился healthcheck — запрос к `/api/v1/info` (в pr-092 заменится на `/healthz`). Без него `docker compose up --wait` считает API готовым сразу после старта контейнера, а uvicorn в этот момент ещё не слушает порт. `astral-sh/setup-uv` указан полной версией: начиная с v8 плавающих тегов вида `v10` у него нет.

## Alembic (pr-005)

- Асинхронный шаблон: миграции идут через тот же драйвер asyncpg, что и приложение.
- Адрес БД берётся из настроек (`VITIGUARD_DATABASE_URL`) и в `alembic.ini` не хранится, чтобы пароль не попал в репозиторий.
- Явные правила именования ограничений (`pk_`, `fk_`, `uq_`, `ix_`, `ck_`): иначе имена придумывает PostgreSQL, и миграции не могут на них сослаться.
- Имена файлов миграций начинаются с даты; новые миграции автоматически проходят Ruff и Black.
- Образ `postgis/postgis` кроме `postgis` ставит `postgis_topology` и `postgis_tiger_geocoder` и добавляет их схемы в `search_path` — через него видно 36 таблиц геокодера TIGER. Миграции подключаются с `search_path=public`, а служебная таблица `spatial_ref_sys` исключена из автогенерации.
- Интеграционные тесты поднимают PostgreSQL + PostGIS через Testcontainers. Тест на `alembic check` падает, если модели изменились, а миграции под них нет.

## PostGIS через миграцию (pr-006)

- Первая миграция выполняет `CREATE EXTENSION IF NOT EXISTS postgis`, откат — `DROP EXTENSION IF EXISTS postgis`. Так база разворачивается одинаково и в Docker, и на сервере, где PostGIS установлен, но не включён.
- Стандартный init-скрипт образа `postgis/postgis` в compose и в тестах подменён пустым (`docker/db/10_postgis.sh`): иначе образ сам ставит `postgis`, `postgis_topology` и `postgis_tiger_geocoder`. Тогда тест не доказал бы, что расширение создаёт миграция, а откат упал бы, потому что от `postgis` зависят два других расширения. Ограничение `search_path=public` из pr-005 оставлено для баз, где лишние схемы уже есть.
- В Docker миграции применяются при старте контейнера API (`alembic upgrade head`, затем uvicorn). CI после запуска стека проверяет, что в базе есть версия миграций и расширение PostGIS.

## Модель пользователей (pr-007)

- Первичные ключи — UUIDv7, их генерирует PostgreSQL 18 (`uuidv7()`). Такие идентификаторы нельзя перебрать по порядку, как целые числа, а индекс по ним не фрагментируется, потому что UUIDv7 растут во времени.
- Роль (`admin`, `agronomist`, `user`) хранится строкой с CHECK-ограничением, а не ENUM-типом PostgreSQL: новую роль можно добавить без `ALTER TYPE`, а откат миграции не требует удалять тип. Автогенерация создала два одинаковых CHECK — в миграции оставлено одно, `ck_users_user_role`.
- «Auth» из формулировки задачи — таблица `refresh_tokens` для выдачи, ротации и отзыва refresh-токенов (pr-017, pr-020). В базе хранится только SHA-256 хэш токена, поэтому утечка таблицы не даёт входа. Токены удаляются вместе с пользователем (`ON DELETE CASCADE`).
- Email уникален; к нижнему регистру его будут приводить схемы API (pr-013, pr-018).
- Все отметки времени — `timestamptz`. Колонка `id` идёт в таблицах первой, отметки времени — последними.
- Тесты моделей работают с настоящей PostgreSQL. Каждый тест выполняется в отдельной транзакции, которая откатывается, поэтому тесты не влияют друг на друга.
- Адрес БД по умолчанию — `127.0.0.1`, а не `localhost`: на Windows с WSL имя `localhost` сначала разрешается в IPv6 `::1`, где порт 5432 может занимать `wslrelay`, и подключение зависает.

## Модель участка виноградника (pr-008)

- Геометрия участка — `MULTIPOLYGON`, а не `POLYGON`: виноградник одного хозяина часто разделён дорогой или лесополосой, и такой участок — это несколько контуров. Одиночный полигон хранится как мультиполигон из одного контура.
- SRID 4326 (WGS 84): в этой системе координат приходят GeoJSON с фронтенда и границы для запросов к Sentinel-2. Площадь считается на эллипсоиде через приведение к `geography` (`ST_Area(geom::geography)`), поэтому перепроецировать в метрическую систему не нужно.
- Колонки и пространственный индекс описаны через GeoAlchemy2. Его помощники для Alembic заменили собственный фильтр `spatial_ref_sys` из pr-005: `include_object` пропускает служебные таблицы PostGIS, а `writer` генерирует `create_geospatial_table` и явный GIST-индекс. С обычным `create_table` GeoAlchemy2 создаёт индекс сам, и миграция падала на повторном создании.
- Участки удаляются вместе с владельцем (`ON DELETE CASCADE`), индекс по `owner_id` нужен для выборки участков пользователя.

## Модель фотодиагностики (pr-009)

- `leaf_images` хранит только ключ объекта в хранилище (MinIO, pr-039) и метаданные: формат, размер, разрешение. Сами файлы в базу не кладутся, чтобы она не разрасталась и не замедлялись резервные копии. CHECK запрещают нулевой размер и разрешение.
- Фото принадлежит пользователю, а участок указывать необязательно: снимок из Telegram-бота (pr-082) приходит без участка. При удалении участка фото остаются (`ON DELETE SET NULL`), при удалении пользователя — удаляются.
- У одного фото может быть несколько записей `disease_results`, по одной на каждый прогон модели. В каждой указаны имя и версия модели, так что результаты разных версий можно сравнить, а история попадает в журнал для дообучения (pr-053).
- Статус `pending` / `completed` / `failed` нужен для асинхронной обработки в Celery (pr-049). Как и роль пользователя, он хранится строкой с CHECK. Ещё одно ограничение не даёт записать `completed` без класса и уверенности.
- Класс болезни хранится строкой, а не перечислением: набор классов определяет обученная модель (ml/pr-003), и он ещё изменится. Вероятности Top-K (pr-045) хранятся в `JSONB`.
- Геотеги из EXIF (pr-051), маски и Grad-CAM (pr-050) и подтверждение агрономом (pr-052) добавятся отдельными миграциями в своих задачах.

## Модель спутниковых индексов (pr-010)

- `satellite_scans` — снимок Sentinel-2, обработанный для одного участка: идентификатор продукта в Copernicus Data Space Ecosystem, время съёмки, облачность сцены (0–100 %), статус обработки. Пара «участок + продукт» уникальна, поэтому повторный запуск задачи Celery (pr-060) не создаст дубликат.
- Значения индексов хранятся в отдельной таблице `vegetation_indices`, по строке на каждый индекс (`ndvi`, `ndre`), а не в колонках `ndvi_mean`, `ndre_mean` у снимка. Так новый индекс добавляется одним значением перечисления, а не четырьмя колонками. Для каждого индекса хранятся среднее, минимум, максимум и стандартное отклонение по пикселям участка: среднее нужно для истории (pr-064, pr-069), разброс — для поиска аномалий (pr-065). CHECK держит значения в диапазоне [-1, 1] и проверяет min ≤ mean ≤ max.
- Сами растры в базу не кладутся: `raster_key` указывает на обрезанный растр в объектном хранилище (pr-062).
- Статус обработки (`pending` / `completed` / `failed`) общий для диагностики и снимков, поэтому `DiagnosisStatus` из pr-009 переименован в `ProcessingStatus` и вынесен в `app/models/enums.py` вместе с помощником для строковых перечислений с CHECK. Имена ограничений в базе не изменились.
- Имена уникальных ограничений теперь включают все колонки (`%(column_0_N_name)s`): для составного ключа получается `uq_satellite_scans_vineyard_id_product_id` вместо вводящего в заблуждение `uq_satellite_scans_vineyard_id`. Имена существующих ограничений по одной колонке остались прежними.

## Модель метеоданных и прогноза (pr-011)

- `weather_data` — почасовые данные Open-Meteo для участка: температура, относительная влажность (0–100 %), осадки (≥ 0). Из них считаются правило трёх десяток, модель Гойданича, индекс Gubler–Thomas (pr-073, pr-074) и признаки для ML (pr-075). Данные хранятся по участку, а не по точке сетки: участков у пользователя немного, а запросы к истории всегда идут по участку.
- Прогноз и факт лежат в одной таблице, их различает флаг `is_forecast`. Пара «участок + час» уникальна, поэтому прогноз на час потом перезаписывается фактическими данными, а не дублируется.
- `disease_risks` — риск милдью или оидиума на участке на дату. Каждый метод (агромодели и ML-модель из ml/pr-018) пишет свою строку, поэтому результаты можно сравнить и показать рядом. Пара «участок + болезнь + дата + метод» уникальна: пересчёт каждые 6 часов (pr-079) обновляет строку, а время последнего пересчёта хранит `updated_at`.
- Оценка риска — число от 0 до 1, уровень `low` / `medium` / `high` хранится отдельно: пороги перевода зависят от метода и задаются при расчёте. Входные значения метода сохраняются в `factors` (JSONB), чтобы объяснить пользователю, откуда взялся риск.
- Болезни и уровни риска — строки с CHECK, как роли и статусы.

## Подключение к БД через AsyncEngine (pr-012)

- Один `AsyncEngine` на приложение создаётся в `lifespan` и закрывается при остановке (`dispose`): все соединения пула возвращаются базе, а не висят «мёртвыми» сессиями. Движок ленивый — соединение открывается при первом запросе, поэтому API стартует и отвечает на `/api/v1/info`, даже если база ещё не поднялась. Движок и фабрика сессий лежат в `app.state`, а не в глобальных переменных: так в тестах можно поднять приложение с другой базой.
- Пул настраивается переменными `VITIGUARD_DATABASE_POOL_SIZE` (10), `..._MAX_OVERFLOW` (10) и `..._POOL_TIMEOUT` (30 с). Размер подобран по числу воркеров и лимиту `max_connections` PostgreSQL (по умолчанию 100): при нескольких воркерах Uvicorn каждый держит свой пул. Когда соединений не хватает, запрос ждёт `pool_timeout` секунд и получает ошибку, а не висит бесконечно.
- `pool_pre_ping=True`: перед выдачей из пула соединение проверяется. Без этого после перезапуска базы или обрыва сети первый запрос падает на «мёртвом» соединении (`connection is closed`); тест `test_pool_replaces_connection_closed_by_server` обрывает соединения через `pg_terminate_backend` и проверяет, что запрос проходит. Цена — один лёгкий запрос на выдачу соединения.
- Фабрика сессий с `expire_on_commit=False`: после `commit` атрибуты объектов остаются доступны. В async-коде их повторное чтение потребовало бы нового запроса, а он упал бы с `MissingGreenlet`.
- Зависимость `SessionDep` даёт сессию на один запрос, но не делает `commit` сама. Автоматический `commit` в зависимости с `yield` выполняется уже после отправки ответа, и ошибка сохранения дошла бы до клиента как успешный ответ. Поэтому `commit` вызывает код, который менял данные (репозитории, pr-014); всё несохранённое откатывается в конце запроса, а при ошибке — сразу.

## Базовые Pydantic-схемы (pr-013)

- Схемы запроса и ответа — разные базовые классы. `RequestSchema` запрещает лишние поля (`extra="forbid"`): опечатка в имени поля даёт ошибку 422, а не молча превращается в «поле не передано». Строки обрезаются по краям. `ResponseSchema` собирается прямо из ORM-объекта (`from_attributes`), поэтому поля, которых нет в схеме (например, `hashed_password`), в ответ не попадают.
- `EntityResponse` — общие `id`, `created_at`, `updated_at` для всех записей: они есть в каждой таблице из миксинов `UUIDPrimaryKeyMixin` и `TimestampMixin`. Время имеет тип `AwareDatetime`: наивное время в ответе — ошибка кода, и она должна всплыть при сериализации, а не уйти клиенту без часового пояса.
- Постраничная выборка: `PageParams` (`page` ≥ 1, `size` от 1 до 100, по умолчанию 20) читается из строки запроса через `PageParamsDep`; неизвестные параметры отклоняются. Верхняя граница `size` защищает базу от запроса «всех записей сразу». `Page[T]` — общий ответ со списком, общим числом записей, номером и размером страницы и вычисляемым полем `pages`; фронтенду для таблицы с пагинацией (frontend/pr-008) это всё, что нужно. Пагинация постраничная (`offset`), а не по курсору: наборы данных небольшие, а интерфейсу нужен переход на произвольную страницу.
- `ErrorResponse` описывает ошибку в формате `{"detail": "…"}`, который отдаёт FastAPI для `HTTPException` и который разбирает клиент фронтенда (`ApiError`). Её подключают к `responses` у маршрутов, чтобы ошибки попадали в OpenAPI.
- Схемы лежат в `app/schemas`, по файлу на тему; схемы сущностей (пользователи, участки и т. д.) будут добавляться рядом вместе с их эндпоинтами.

## Базовый CRUD и паттерн Repository (pr-014)

- `Repository[Model]` — доступ к таблице одной модели: `get`, `get_or_raise`, `list` (страница и общее число записей с фильтрами и сортировкой), `create`, `update`, `delete`. Конкретный репозиторий — подкласс с полем `model` и своими запросами (например, поиск пользователя по email в pr-018). Репозиторий не знает про HTTP и FastAPI: ему нужна только сессия.
- Репозиторий только отправляет изменения в базу, но не вызывает `commit`. Это уточняет pr-012: транзакцию фиксирует код, который ею владеет (сервис или эндпоинт), поэтому несколько репозиториев могут работать в одной транзакции и откатываться вместе.
- Изменения делаются внутри savepoint (`begin_nested`), и это важно. Если `flush` падает на нарушении ограничения вне savepoint, сессия остаётся в состоянии «ожидает отката» (`PendingRollbackError`) и дальше не работает; проверено тестом. Внутри savepoint откатывается только он: добавленный объект убирается из сессии, изменённый возвращается к состоянию в базе, а сессия остаётся рабочей.
- Ошибки предметной области — `NotFoundError` (404) и `ConflictError` (409) в `app/core/errors.py`; обработчик превращает их в `{"detail": "…"}`, как ошибки FastAPI. Слои ниже API не знают про коды ответов. В `ConflictError` превращается только нарушение уникальности (SQLSTATE 23505): остальные `IntegrityError` (внешний ключ, CHECK) — это ошибка в коде или данных, и скрывать их под «запись уже существует» нельзя.
- Сообщения об ошибках задаются в подклассе (`not_found_message`, `conflict_message`) по-русски: их показывает интерфейс.
- Без явной сортировки `list` упорядочивает записи по `id`. UUIDv7 растёт во времени, поэтому порядок стабильный и совпадает с порядком создания, а страницы не «плывут» между запросами. Общее число считается отдельным запросом `count(*)` с теми же условиями.
- `update` проверяет имена полей: неизвестное поле — `ValueError`, а не обычный атрибут, который `setattr` создал бы молча. После изменения объект перечитывается (`refresh`): `updated_at` выставляет база, а читать его в async-коде без перезагрузки нельзя.

## Celery с брокером Redis (pr-015)

- Redis — и брокер очереди, и хранилище результатов, в разных базах (`/0` и `/1`): очередь можно очистить, не потеряв результаты, а результаты — не задев очередь. Отдельный RabbitMQ не нужен: Redis уже есть в стеке (кэш ГИС-запросов, pr-037), а нагрузка на очередь небольшая.
- Приложение Celery создаётся функцией `create_celery(settings)`, как и FastAPI-приложение: тесты поднимают его со своими адресами. Модуль `app/worker/celery_app.py` держит готовый экземпляр для команды `celery -A app.worker.celery_app worker`. Задачи объявлены через `shared_task` с явными именами (`system.ping`): имя не зависит от пути модуля, и переименование файла не ломает задачи, уже стоящие в очереди. Модули с задачами перечисляются в `TASK_MODULES`.
- Только JSON: pickle позволяет выполнить произвольный код любому, кто сможет записать в Redis. Платой становится то, что аргументы и результаты задач должны быть простыми данными (идентификаторы, числа, строки): в задачу передаётся `image_id`, а не изображение.
- `task_acks_late` и `worker_prefetch_multiplier=1`: задача подтверждается после выполнения, и если воркер упал на полпути, она возвращается в очередь; воркер берёт по одной задаче, чтобы долгая обработка снимка не стояла в буфере занятого воркера, пока соседний простаивает. Цена — задачи должны быть идемпотентными: повторный запуск даёт тот же результат. Redis возвращает неподтверждённую задачу по истечении `visibility_timeout` (1 час), он должен быть больше самой долгой задачи.
- Лимиты времени: мягкий (300 с) даёт задаче шанс корректно завершиться (`SoftTimeLimitExceeded`), жёсткий (330 с) останавливает процесс. Мягкий обязан быть меньше жёсткого — это проверяет валидатор настроек. Результаты хранятся час.
- В Compose воркер — отдельный сервис из того же образа: код и зависимости одни, масштабируется независимо от API (`docker compose up --scale worker=3`). Его healthcheck — `celery inspect ping`. Общие переменные окружения вынесены в `x-app-environment`. CI проверяет всю цепочку: из контейнера API отправляется задача `system.ping`, и воркер должен вернуть `pong`.
- Типы для Celery — пакет `celery-types` (dev-зависимость): сам Celery их не поставляет, а отключать проверку mypy ради него не нужно.

## Хэширование паролей: Argon2 через pwdlib (pr-016)

- Из roadmap «Argon2 / Passlib» выбран **Argon2**, но не через Passlib. Passlib не обновлялся с 2020 года (последний выпуск 1.7.4) и перестаёт работать с новыми версиями зависимостей, а его создатель больше его не поддерживает. Вместо него — `pwdlib`: тот же подход (набор хэшеров, проверка с обновлением хэша), активная поддержка, и именно его документация FastAPI сегодня рекомендует. Сам алгоритм считает `argon2-cffi`.
- Argon2id — победитель конкурса Password Hashing Competition и рекомендация OWASP. Он требует много памяти (64 МиБ на один хэш), поэтому перебор паролей на видеокартах и специализированных чипах дорог, в отличие от bcrypt и PBKDF2. Параметры — значения библиотеки по умолчанию (профиль RFC 9106 для серверов: 64 МиБ, 3 прохода, 4 потока); один хэш занимает около 150 мс. Соль случайная и хранится в самой строке хэша вместе с параметрами, поэтому одинаковые пароли дают разные хэши, а проверка не зависит от внешних настроек.
- Хэширование — чистая нагрузка на процессор. Выполненное прямо в обработчике, оно блокировало бы цикл событий: пока один пользователь входит, остальные запросы ждали бы 150 мс. Поэтому из асинхронного кода пароль обрабатывается в потоке (`ahash_password`, `averify_and_upgrade` через `asyncio.to_thread`).
- Если пользователя с таким email нет, `verify_password(пароль, None)` всё равно выполняет полную проверку на заглушке. Без этого ответ «пользователя нет» приходил бы на ~150 мс быстрее ответа «пароль неверный», и по времени ответа можно было бы узнавать, какие email зарегистрированы. Тот же принцип, что и в форме восстановления пароля (frontend/pr-013).
- `verify_and_upgrade` возвращает новый хэш, если старый сделан с более слабыми параметрами. При входе его нужно записать вместо старого (backend/pr-019): стоимость хэширования можно повышать без принудительного сброса паролей.
- Нераспознаваемая строка в колонке `hashed_password` означает неудачный вход, а не ошибку сервера: повреждённая запись не должна ронять запрос и раскрывать причину.
- Максимальную длину пароля ограничивает схема запроса (128 символов, как в форме регистрации): Argon2 принимает длинные строки, но пароль в мегабайты был бы дешёвым способом нагрузить сервер.

## JWT: access- и refresh-токены (pr-017)

- Оба токена — JWT, подписанные HS256 одним секретным ключом сервиса (`VITIGUARD_SECRET_KEY`). Симметричная подпись подходит, пока токены выпускает и проверяет один сервис: асимметричные ключи (RS256 / EdDSA) нужны, когда проверять токены должны посторонние сервисы, которым нельзя доверять ключ выпуска. Если появятся отдельные сервисы-потребители, алгоритм меняется в одном месте (`ALGORITHM`).
- **Access-токен** живёт 15 минут (`VITIGUARD_ACCESS_TOKEN_TTL_MINUTES`) и несёт идентификатор пользователя (`sub`), роль (`role`), издателя (`iss`), тип, время выпуска и истечения. Роль внутри токена позволяет проверять права без обращения к БД; цена — изменение роли вступает в силу не позже чем через 15 минут. Отозвать access-токен нельзя, поэтому он короткий: украденный перестаёт работать сам.
- **Refresh-токен** живёт 30 дней (`VITIGUARD_REFRESH_TOKEN_TTL_DAYS`), содержит только `sub`, тип и случайный `jti`, и дополнительно хранится в таблице `refresh_tokens` (SHA-256 хэш, срок, время отзыва, pr-007). Подпись позволяет отбросить подделку, не обращаясь к БД, а запись в БД — отозвать токен при выходе или краже и менять его при каждом обновлении (pr-020). Случайный `jti` делает каждый токен уникальным: два токена одного пользователя, выпущенные в одну секунду, не совпадут, и `unique` по хэшу не срабатывает ложно.
- Проверка токена строгая. Алгоритм передаётся явно, а не берётся из заголовка токена: иначе можно подсунуть `alg: none` (подпись не нужна) или другой алгоритм. Обязательны `exp`, `iat`, `sub`, `iss` и `type`; издатель должен совпасть. Тип токена проверяется: refresh-токен нельзя использовать как access (он живёт 30 дней и лежит в cookie), и наоборот. Любая проблема — ответ 401 с заголовком `WWW-Authenticate: Bearer`; для просроченного токена текст «Срок действия токена истёк», для остальных — «Недействительный токен» без подробностей, чтобы не подсказывать, что менять в подделке. Каждый случай подделки (чужой ключ, изменённое содержимое, `alg: none`, HS512, нет обязательного поля, чужой издатель, неверный `sub` и роль, мусор) покрыт тестом.
- Секретный ключ: в `local` и `test` есть публичный ключ для разработки, а в `staging` и `production` приложение не запустится с ним или с ключом короче 32 символов. Ошибка при старте лучше, чем сервис, токены которого может выписать любой, кто прочитал репозиторий. Ключ — `SecretStr`: он не попадает в `repr` настроек и логи.
- Хэш токена для БД — обычный SHA-256, без соли и медленного алгоритма, в отличие от паролей: токен случаен (и содержит подпись), перебрать его нельзя, а проверка выполняется при каждом обновлении, и медленный хэш был бы лишней нагрузкой.
- Время можно передать функциям выпуска (`now`): тесты проверяют сроки без ожидания.
- Расхождения времени между серверами (допуск `leeway`) не вводятся: токены выпускает и проверяет один сервис; при нескольких серверах их часы синхронизирует NTP.

## Регистрация `/auth/register` (pr-018)

- Слои: роут принимает запрос, сервис `register_user` хэширует пароль и фиксирует транзакцию, репозиторий `UserRepository` только пишет в базу. Так правила регистрации не размазаны по HTTP-коду и проверяются отдельно.
- Свободен ли email, отдельным запросом не проверяется: два одновременных запроса прошли бы такую проверку оба. Уникальность гарантирует база, нарушение превращается в ответ 409.
- Email приводится к нижнему регистру в схеме запроса, а CHECK `ck_users_email_lowercase` не даёт записать адрес в другом регистре в обход API. Миграция заодно приводит уже сохранённые адреса.
- Пароль: от 8 до 128 символов, хотя бы одна буква и одна цифра — те же правила, что в форме регистрации; пробелы не обрезаются. Верхняя граница не даёт нагружать сервер хэшированием огромных строк.
- Роль при регистрации — только `user` или `agronomist`; администратора назначает администратор.
- Ответ 422 переопределён: стандартный ответ FastAPI возвращает введённые значения в поле `input`, то есть отправленный пароль попадал бы в тело ответа и в логи.

## Вход `/auth/login` (pr-019)

- Контракт согласован с фронтендом (frontend `docs/decisions.md`, pr-014): JSON с email и паролем, в ответе `{access_token, token_type: "bearer"}`, refresh-токен — в cookie `refresh_token` с флагами `HttpOnly; Secure; SameSite=Strict; Path=/api/v1/auth`. Скрипт на странице cookie не прочитает, чужой сайт не заставит браузер её отправить, а узкий `Path` не даёт ей уходить с остальными запросами. Путь берётся из настройки префикса API.
- Неизвестный email и неверный пароль дают одинаковый ответ 401 «Неверный email или пароль». Для неизвестного email пароль всё равно проверяется на заглушке (pr-016), поэтому ни текст, ни время ответа не выдают, зарегистрирован ли адрес.
- Об отключённой учётной записи (ответ 403) сообщается только после верного пароля.
- Если хэш пароля сделан со старыми параметрами Argon2, при входе он заменяется актуальным — стоимость хэширования растёт без сброса паролей.
- При входе в `refresh_tokens` сохраняется SHA-256 хэш выданного refresh-токена и срок его действия: так его можно будет ротировать (pr-020) и отозвать при выходе.
- Пароль при входе только обязателен (1–128 символов): правила сложности проверяются при регистрации, а старый пароль мог быть задан по прежним правилам.
- Флаг `Secure` отключается настройкой `VITIGUARD_REFRESH_COOKIE_SECURE=false` — только для тестов и окружений без HTTPS.

## Обновление токена и выход (pr-020)

- `POST /auth/refresh` читает cookie `refresh_token` и выполняет ротацию: старый refresh-токен отзывается, выдаются новые access- и refresh-токены, новая cookie — с теми же флагами, что при входе. Украденный токен работает не дольше, чем до следующего обновления у настоящего владельца.
- Токен проверяется дважды: подпись, срок и тип JWT, а затем запись в `refresh_tokens` по SHA-256 хэшу. Токен с верной подписью, которого сервер не выдавал, не принимается; access-токен вместо refresh — тоже.
- Повторно пришедший отозванный токен — признак кражи: у кого-то есть его копия. Кто из двоих злоумышленник, неизвестно, поэтому отзываются все сессии пользователя, и войти заново можно только с паролем. Отзыв фиксируется в базе до ответа 401.
- Строка токена блокируется на время ротации (`SELECT … FOR UPDATE`): два одновременных обновления одним токеном выполняются по очереди, второе увидит токен отозванным. Фронтенд объединяет одновременные обновления в один запрос (frontend pr-014), поэтому в обычной работе это не срабатывает.
- `POST /auth/logout` отзывает токен и удаляет cookie (тот же путь и флаги — иначе браузер её не удалит), всегда отвечая 204: повторный выход или выход без cookie дают тот же результат — сессии нет. Отдельной задачи на выход в плане нет, но он нужен фронтенду (`useLogout`), а логически это часть работы с refresh-токенами.
- Отключённый пользователь обновить токен не может.

## Проверка access-токена: зависимость, а не middleware (pr-021)

- В формулировке задачи — «middleware и зависимости безопасности». Проверка сделана зависимостью FastAPI `CurrentUserDep` со схемой `HTTPBearer`, без общего middleware. Защищённость эндпоинта видна в его сигнатуре, а схема попадает в OpenAPI (кнопка «Authorize» в Swagger). Middleware проверял бы все запросы и держал бы список открытых путей (`/auth/login`, `/docs`, …): ошибка в этом списке молча открыла бы эндпоинт.
- Нет заголовка, другая схема (`Basic`), поддельный, просроченный или refresh-токен вместо access — ответ 401 с `WWW-Authenticate: Bearer`. Стандартный `HTTPBearer` на отсутствие заголовка отвечает 403, поэтому он включён с `auto_error=False`, а ошибку формирует зависимость.
- Пользователь читается из базы на каждый запрос (один запрос по первичному ключу), роль тоже берётся из базы, а не из токена. Отключённый или удалённый пользователь теряет доступ сразу, а не когда истечёт токен (до 15 минут), смена роли действует сразу.

## Ролевая модель доступа (pr-022)

- Доступ по ролям задаёт фабрика зависимостей `require_roles(...)` с явным списком разрешённых ролей. Готовые зависимости: `CurrentUserDep` — любой вошедший, `AgronomistDep` — агроном или администратор, `AdminDep` — только администратор. Иерархии ролей нет: по эндпоинту сразу видно, кому он открыт, а новая роль не получит чужих прав случайно.
- Матрица доступа:

| Роль | Любой вошедший | Агроном | Администратор |
|---|---|---|---|
| `user` (виноградарь) | да | нет | нет |
| `agronomist` | да | да | нет |
| `admin` | да | да | да |

- Нет нужной роли — 403 «Недостаточно прав» без `WWW-Authenticate`: пользователь известен, повторный вход не поможет. Не вошёл — 401, как в pr-021.
- Роль берётся из базы на каждый запрос (pr-021), поэтому понижение роли действует сразу, даже с ранее выданным токеном.
- Роль администратора при регистрации выбрать нельзя (pr-018); её назначает администратор (управление пользователями — frontend pr-091).

## Профиль `/users/me` (pr-023)

- `GET /users/me` возвращает текущего пользователя, `PATCH /users/me` меняет имя. Оба эндпоинта — только для вошедших (`CurrentUserDep`), в OpenAPI отмечены схемой Bearer.
- Через профиль меняется только имя. Email, роль и признак активности схема `UserUpdate` не принимает: лишнее поле даёт 422, а не тихо игнорируется — так попытка выдать себе роль администратора видна сразу, а не выглядит как успешный запрос.
- Имя обрезается по краям и должно быть не короче 2 символов — как при регистрации.
- Смена пароля в профиль не входит: она появится вместе со сбросом пароля по email (pr-024).

## Сброс пароля по email (pr-024)

- Контракт фронтенда (frontend pr-013): `POST /auth/password-reset` с `{email}` всегда отвечает 202 с пустым телом — ответ не выдаёт, есть ли аккаунт; `POST /auth/password-reset/confirm` с `{token, new_password}` отвечает 204, при неверной или устаревшей ссылке — 400.
- Ключ — случайная строка (`secrets.token_urlsafe`), в таблице `password_reset_tokens` только её SHA-256. Ключ одноразовый, действует 60 минут (`VITIGUARD_PASSWORD_RESET_TTL_MINUTES`), работает только последняя отправленная ссылка.
- Новый пароль проверяется по тем же правилам, что при регистрации; неудачная попытка ключ не тратит. После смены пароля отзываются все refresh-токены — пользователь выходит на всех устройствах.
- SMTP, а не API SendGrid: стандартный протокол работает и с Mailpit в разработке, и с любым провайдером (у SendGrid тоже есть SMTP). Письмо отправляет задача Celery с повторами при сбоях почтового сервера, поэтому ответ API не ждёт почту.
- В compose добавлен Mailpit: письма никуда не уходят и видны на http://127.0.0.1:8025.

## ML-проект в `ml/` (ml/pr-001)

- Код обучения — отдельный uv-проект в `ml/` со своим `pyproject.toml` и lock-файлом. PyTorch и другие библиотеки обучения занимают гигабайты: в образе API и в CI бэкенда они не нужны.
- Зависимости разделены: основные (NumPy, Pillow, Pydantic, PyYAML) — для подготовки данных и тестов; группа `train` (PyTorch, torchvision, timm, Albumentations, scikit-learn) ставится только для обучения, обычно в Google Colab или Kaggle с GPU (`uv sync --group train`).
- Параметры эксперимента — в YAML-конфиге, проверяемом Pydantic. Опечатка в имени параметра, доли выборок, не дающие в сумме 1, повтор класса — ошибка при загрузке, а не тихая порча эксперимента. Конфиг наследует базовый через `extends`, вложенные разделы объединяются.
- `set_seed` фиксирует генераторы Python, NumPy и PyTorch (включая детерминированный режим cuDNN), чтобы результаты экспериментов в отчёте можно было повторить.
- Классы диагностики: `healthy`, `black_rot`, `esca`, `leaf_blight`, `downy_mildew`, `powdery_mildew`. Порядок в конфиге — порядок выходов модели.
- Данные и результаты обучения (`ml/data`, `ml/artifacts`) в git не хранятся. В CI для `ml/` отдельная задача: mypy и тесты без тяжёлых зависимостей.

## Подготовка PlantVillage (ml/pr-002)

- Источник — репозиторий `spMohanty/PlantVillage-Dataset` (Hughes, Salathé, 2015), цветные изображения. Скачиваются только четыре папки винограда: клон без истории (`--depth 1`), без содержимого файлов по умолчанию (`--filter=blob:none`) и с `sparse-checkout`. Весь датасет — 54 тыс. изображений 38 классов, винограду из них нужно 4 062.
- Папки отображаются на коды классов проекта: `black_rot`, `esca`, `leaf_blight`, `healthy`. Милдью и оидиума в PlantVillage нет — они добавляются из других источников (ml/pr-003, ml/pr-004).
- Файлы сохраняются под именем из SHA-256 содержимого. Одинаковые изображения совпадают по хэшу и в набор попадают один раз: дубликат в обучающей и тестовой выборке одновременно завысил бы оценку качества. Нечитаемые файлы и файлы не-изображения пропускаются, причина считается.
- Манифест `manifest.csv` (путь, класс, источник, SHA-256, ширина, высота) — общий формат для всех наборов: по нему делается разбиение на выборки (ml/pr-005) и статистика для отчёта.
- Результат на реальных данных: 4 062 изображения 256×256 — black_rot 1 180, esca 1 383, leaf_blight 1 076, healthy 423; дубликатов и повреждённых файлов нет. Подготовка занимает около 2 минут.

## Наборы с милдью и оидиумом, удаление повторов (ml/pr-003)

- Источник милдью и оидиума — Niphad Grape Leaf Disease Dataset (NGLD), Mendeley Data, версия 5, DOI 10.17632/8nnd2ypcv3.5, лицензия CC BY 4.0: столовый виноград, 2 726 фото 256×256, папки Downy Mildew, Powdery Mildew, Healthy Leaves, Bacterial Leaf Spot. Скачивается без учётной записи через публичный API Mendeley. Рассмотрены и другие наборы под CC BY 4.0: HERMOS (914 снимков с разметкой рамками), «Downy Mildew and Powdery Mildew Symptoms» и набор симптомов милдью на сорте Мерло. Они размечены для детекции, а не по папкам-классам, и пригодятся позже для полевой оценки.
- «Bacterial Leaf Spot» (100 фото) не берётся: такого класса в системе нет, а для виноградников Молдовы эта болезнь не основная.
- Импорт «папка = класс» вынесен в общий модуль `data/folders.py`: PlantVillage и NGLD подготавливаются одинаково.
- В манифест добавлен перцептивный хэш dHash (64 бита). SHA-256 находит только побайтовые копии, а dHash — и пересжатые или уменьшенные копии одного снимка. Повтором считается совпадение dHash. Выборочная проверка найденных пар глазами: во всех случаях это один и тот же лист.
- `data/combine.py` объединяет наборы в общий манифест с едиными классами. При повторе остаётся экземпляр из источника, стоящего раньше в списке. Повторы с разными классами выводятся отдельно, их нужно проверять вручную.
- Результат на реальных данных: в NGLD 333 побайтовые копии и ещё 313 копий по dHash, почти все в классе «здоровые» (1 254 → 622). Конфликтов разметки нет. Итоговый набор — 6 042 изображения:

| Класс | PlantVillage | NGLD | Всего |
|---|---|---|---|
| healthy | 423 | 622 | 1 045 |
| black_rot | 1 180 | 0 | 1 180 |
| esca | 1 383 | 0 | 1 383 |
| leaf_blight | 1 076 | 0 | 1 076 |
| downy_mildew | 0 | 966 | 966 |
| powdery_mildew | 0 | 392 | 392 |

- Ограничения, которые нужно учесть при обучении и в отчёте:
  - каждая болезнь представлена только одним источником, поэтому модель может научиться различать источники, а не болезни. Признак этого — путаница здоровых листьев из разных наборов; её нужно проверять по матрице ошибок с разбивкой по источнику;
  - листья в NGLD сняты по одному на белом фоне, как в PlantVillage, поэтому полевой тестовый набор (ml/pr-004) по-прежнему нужен;
  - оидиума меньше всего (392), при обучении нужны веса классов.

## Разбиение на выборки, дисбаланс, аугментации (ml/pr-005)

- Разбиение 70 / 15 / 15 % (train / val / test) стратифицировано по паре «класс + источник» с фиксированным seed из конфига. В каждую выборку попадает та же доля каждого класса из каждого источника. Иначе, например, здоровые листья NGLD могли бы почти все уйти в обучение, а в тесте остались бы только листья PlantVillage, и оценка качества была бы искажена. Повторы удалены до разбиения (ml/pr-003), поэтому копии одного снимка не окажутся в разных выборках. Результат — `splits.csv` (манифест + выборка) и `class_stats.json`.
- Дисбаланс в обучающей выборке — 3,53 (эска 968 против оидиума 274). Веса классов для функции потерь — по схеме `balanced` из scikit-learn: обратно пропорциональны числу примеров, средний вес по примерам равен 1. Вес оидиума — 2,57, эски — 0,73.

| Класс | train | val | test | Вес |
|---|---|---|---|---|
| healthy | 731 | 156 | 158 | 0,96 |
| black_rot | 826 | 177 | 177 | 0,85 |
| esca | 968 | 207 | 208 | 0,73 |
| leaf_blight | 753 | 161 | 162 | 0,94 |
| downy_mildew | 676 | 145 | 145 | 1,04 |
| powdery_mildew | 274 | 59 | 59 | 2,57 |

- Аугментации обучения (Albumentations) имитируют отличия полевого снимка от лабораторного: случайное кадрирование и масштаб (60–100 % площади), отражения, поворот до 30°, яркость и контраст, небольшой сдвиг цвета, размытие (как при съёмке с рук), случайные «вырезанные» прямоугольники (лист частично закрыт). Нормализация — по статистике ImageNet, на которой предобучены модели. На проверке и тесте — только изменение размера и нормализация, без случайности.
- Albumentations входит в группу `train`, но в CI тесты аугментаций выполняются через `uv run --with albumentations`: без PyTorch и без изменения lock-файла.

## Полевой тестовый набор из HERMOS (ml/pr-004)

- В плане был набор собственных фото из виноградников Молдовы, но доступа к виноградникам нет. Вместо него — полевые снимки открытого набора HERMOS: Mendeley Data, версия 2, DOI 10.17632/j4xs3kh3fd.2, лицензия CC BY 4.0, виноградники Западной Анатолии (Турция). В описании набора заявлено 914 снимков, фактически в версии 2 — 492 снимка (в основном 6000×4000) и 13 904 рамки в формате Pascal VOC. Архив весит 3,1 ГБ.
- Снимок HERMOS — сцена из многих листьев, и на одном кадре часто есть и здоровые, и больные листья. Поэтому метка «на весь снимок» была бы неверной. Вместо этого вырезается каждая рамка с окружением: квадрат со стороной в 3 раза больше рамки, но не меньше 384 пикселей. У края снимка окно сдвигается внутрь. Вырезка уменьшается до 256×256 — как в обучающих наборах.
- Отбрасываются: вырезки, в окно которых попадает центр рамки другого класса (иначе метка «здоровый» досталась бы листу рядом с пятном болезни); вырезки, чей центр уже внутри принятого окна того же класса (почти одинаковые кадры); классы «dead arm» и случайные «dog».
- Результат: 4 936 вырезок — healthy 2 087, powdery_mildew 2 480, downy_mildew 369; отброшено 7 065 рамок, повторов по dHash нет. Подготовка занимает около 4 минут.
- Набор используется **только для теста** и в обучение не входит. Сравнение качества на лабораторной тестовой выборке и на этом наборе (ml/pr-010) показывает, насколько модель теряет точность в поле.
- Ограничения, которые нужно указывать вместе с результатами:
  - **Масштаб.** Вырезка — крупный план участка листа, а не лист целиком, как в обучающих наборах. Тест строже реальной съёмки, поэтому результат на нём — оценка снизу.
  - **Шум в метках.** Метка — это рамка автора набора. Выборочная проверка показала, что на части вырезок симптомы оидиума едва различимы.
  - **Классы.** Всего три класса (чёрной гнили, эски и пятнистости в наборе нет), милдью мало (369).
  - **Регион.** Снимки из Турции, а не из Молдовы, хотя климат и болезни сходны.

## Текущая погода из Open-Meteo (pr-071)

- Open-Meteo — бесплатный сервис без ключа API с моделями высокого разрешения для Европы. Клиент `app/integrations/open_meteo.py` запрашивает температуру воздуха на 2 м, относительную влажность и осадки — то, что нужно агромоделям (pr-073, pr-074). Время запрашивается и хранится в UTC: сезонный переход часов не создаёт дыр и повторов в почасовых данных.
- Один `httpx.AsyncClient` на всё приложение создаётся при запуске и закрывается при остановке: соединения с внешними сервисами переиспользуются. Таймаут — 10 с (`VITIGUARD_EXTERNAL_HTTP_TIMEOUT`), при сбое соединения — до двух повторов.
- Любой сбой источника — сетевая ошибка, таймаут, ответ с ошибкой, не-JSON или JSON без нужных полей — превращается в `ExternalServiceError` и ответ 502 с понятным текстом, а не в 500 с трассировкой. Ответ проверяется Pydantic-схемой, поэтому изменение формата у Open-Meteo не приведёт к записи мусора в базу.
- `GET /weather/current?latitude=…&longitude=…` — только для вошедших: иначе эндпоинт стал бы бесплатным посредником к Open-Meteo для кого угодно, а лимит запросов к сервису общий на весь сервер. Координаты проверяются (широта ±90, долгота ±180).
- Клиент тестируется без сети через `httpx.MockTransport`; эндпоинт — с подменой клиента через `dependency_overrides`.

## Исторические метеоданные (pr-072)

- Архив Open-Meteo запрашивается почасово за период (не длиннее 366 дней за раз — длинную историю фоновая задача загрузит частями) по точке внутри участка.
- Точка участка — `ST_PointOnSurface`, а не центроид. У участка сложной формы (например, в виде буквы «С») центроид может оказаться за его границей; тест это проверяет на таком участке.
- Записи пишутся одним запросом `INSERT … ON CONFLICT (vineyard_id, observed_at) DO UPDATE`. Повторный импорт того же периода обновляет строки, а не дублирует их, а фактические данные заменяют прогноз на тот же час.
- Часы без значений в архиве (последние дни публикуются с задержкой) пропускаются, а не записываются нулями. «0 мм осадков» и «нет данных» — разные вещи, и ноль исказил бы правило трёх десяток. Ряды разной длины в ответе считаются ошибкой источника (502).
- Импорт пока вызывается из кода (сервис `import_weather_history`). По расписанию его будет запускать Celery Beat (pr-079), когда появятся эндпоинты участков.
